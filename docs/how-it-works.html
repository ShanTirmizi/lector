How Lector works

A Chrome extension that reads a page aloud with a voice that runs on your own machine, and marks each word as it is spoken. This page shows the parts, follows one real run, and points at the code.

The three parts

Chrome gives an extension several separate places to run code. Lector uses three, because each can do something the others cannot.

  • Why not play sound in the page? Many sites forbid it with their security policy, and the 330 MB model would have to load again on every tab.
  • Why a worker inside the offscreen document? Making speech is heavy. In a worker it cannot make the clock that drives the highlighting stutter.

One real run: you press Alt+R on an article

  1. The command arrives. Chrome hands the shortcut to the service worker, which sends toggle to the tab. src/background/index.ts
  2. The page finds its article. Every paragraph votes for the container it sits in. The container with the most paragraph text wins. Menus, sidebars and footers are thrown out. src/content/blocks.ts
  3. Text becomes sentences. Each one remembers exactly which characters of the page it covers. Citation markers and web addresses are cut from what is spoken, but the map back to the page stays exact. src/content/segment.ts
  4. The sentences travel to the engine. The page asks the service worker to make sure the offscreen document exists, then connects to it and sends the whole list. src/content/engine-client.ts
  5. The voice speaks the first sentence. Text becomes phonemes, phonemes go through the model, and out come sound samples plus how long each phoneme lasted. src/offscreen/engine.ts
  6. Sound plays, and the next sentences are prepared. About 40 seconds of speech is kept ready ahead of you. src/offscreen/index.ts
  7. The page lights up words. Eight times a second the engine reports the audio position. Between reports the page runs its own clock, 60 times a second, and marks whichever word has started. src/content/reader.ts

How a word knows when to light up

This is the part most read-aloud tools get from a server. Lector gets it from the model itself.

  • Easy case: the text and the phoneme string have the same number of words. Pair them in order.
  • Hard case: "2024" becomes three spoken words, and "of the" becomes one. Lector then phonemises each word on its own and lines that sequence up against the real one with an edit-distance alignment, the same idea a spell checker uses. src/offscreen/align.ts
  • Speed does not change any of this. The audio is made once at normal speed. The browser plays it faster with the pitch kept, and the timings are simply scaled.

Highlighting without touching the page

The obvious way to highlight a word is to wrap it in a coloured element. That changes the page's HTML, which breaks sites built with frameworks that own their own DOM.

Lector uses the CSS Custom Highlight API instead. It is given a range of characters and a colour, and the browser paints it. The page's HTML is never changed.

For this to work every character of the extracted text needs a way back to the page. A block keeps two arrays the same length as its text:

  • which text node each character came from
  • its offset inside that node

That is why a citation marker in the middle of a sentence is skipped by the voice and by the highlight alike.

PDFs and Google Docs

  • PDFs open in Lector's own view. Pages are drawn by PDF.js with an invisible copy of the text on top, so the highlighter has something to mark.
  • Google Docs draws its text on a canvas, so there is nothing in the page to read or highlight. Lector downloads the document's own export as you, strips it to plain structure, and shows it as a clean page. src/document/index.ts

Try this

See the word timings. Run node scripts/voice-check.mjs. It speaks four sentences with the real engine, transcribes the audio back with a speech recogniser, and prints how fast synthesis ran.
Break the alignment on purpose. In src/offscreen/align.ts, make the easy case always run (skip the edit-distance step). Read a sentence with a year in it and watch the highlight drift after the number.
Move the reading line. In src/content/scroller.ts, change TARGET from 0.32 to 0.5 and feel how different the scrolling is when the sentence sits mid-screen.
Test it on a hard page. Run node scripts/try.mjs <url> on a site you read. It prints the sentences Lector chose, so you can see at once if it picked up a menu or missed a paragraph.

How it was checked

  • npm test loads the built extension in Chromium and drives it: reading, word order, pause, speed, voice change, paragraph and selection buttons, resume, settings, the PDF view and the document view.
  • scripts/voice-check.mjs confirms the speech is intelligible and measures speed (about 4× faster than real time on WebGPU).
  • Not checked by a machine: how the voice sounds to a person, real Google Docs and Gmail (both need a signed-in account), and local file:// PDFs.
